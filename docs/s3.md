# S3 Gateway (VersityGW)

`https://s3.jkrumm.com` — an S3 API over existing HomeLab folders, Tailscale-only (grey-cloud
A record → HomeLab Tailscale IP, Caddy → `versitygw:7070`). It is the scripted/agent door to
the files; Samba stays the Finder door, Filebrowser the web door.

## Why VersityGW, posix backend

Objects are plain files at their normal paths. Samba, restic, Immich's external library and
rsync keep reading the same tree; nothing is stored in an opaque format. Garage, SeaweedFS,
RustFS and Ceph RGW all chunk data into their own format, and MinIO community is archived —
none of them can serve an existing directory tree.

## Buckets

A bucket is a top-level directory under the gateway root (`~/ssd/versitygw/root`); each one
is a bind mount in `docker-compose.yml`. S3 shows the same two roots as Samba and Filebrowser.

| Bucket | Host path |
|-|-|
| `ssd` | `~/ssd/SSD` (Bilder, Dokumente, Bücher, …) |
| `hdd` | `/mnt/hdd` (fuji, inbox, …) |
| `weatherorb-archive` | `/mnt/hdd/weatherorb-archive` — also under `hdd/`; its own bucket only for weatherorb's push key; sealed immutable (Caveats) |

All mounts are rw: bucket ACLs and policies are xattrs on the bucket directory, which a `:ro`
bind cannot hold. Files written through S3 land as `jkrumm` 0644 (the container runs as
1000:1000), so it can't read or write anything owned by another uid (e.g. root-owned app state).

**Adding a bucket:** add the bind mount → `make deploy` → convert it (below) → add a row here.

## Keys

| 1Password item (`homelab` vault) | VersityGW role | Used by |
|-|-|-|
| `versitygw-root` | root | Server only — IAM admin, bucket policies |
| `s3-admin` | admin (full access) | MacBook — `hl`, Shutterflow |
| `s3-agent` | user — everything except delete, on `ssd` + `hdd` | Mini agents, via `secrets-run` |
| `s3-weatherorb` | user — read + write (no delete) on `weatherorb-archive` only | weatherorb's archive push from the mini (ADR 0009) |

Each item has `ACCESS_KEY_ID`, `SECRET_ACCESS_KEY`, `ENDPOINT`, `REGION` (`us-east-1` — the
IAM API only accepts that region). Users live in the internal IAM file under
`~/ssd/versitygw/iam` (not backed up — recreate from 1Password).

A `user`-role key's `ListBuckets` returns nothing (it owns no bucket); address buckets by
name.

## Operations

Admin CLI (runs inside the container, root key from 1Password):

```bash
ssh homelab 'bash -c '"'"'op run --env-file=<(printf "%s\n" RA=op://homelab/versitygw-root/ACCESS_KEY_ID RS=op://homelab/versitygw-root/SECRET_ACCESS_KEY) -- \
  sh -c "docker exec -e ADMIN_ACCESS_KEY_ID=\$RA -e ADMIN_SECRET_ACCESS_KEY=\$RS versitygw versitygw admin -er http://127.0.0.1:7070 list-users" < /dev/null'"'"''
```

Convert a new or pre-existing directory into a bucket (writes the `acl` + `ownership` xattrs on
the bucket dir; files are untouched). Run as a one-off with every bucket bind mounted:

```bash
ssh homelab 'docker run --rm --user 1000:1000 --entrypoint versitygw \
  -v /home/jkrumm/ssd/versitygw/root:/data/root -v <host-dir>:/data/root/<bucket> \
  versity/versitygw:latest utils convert-posix-dataset --posix-root-dir /data/root --access-key-id vgw-root'
```

Bucket policy (root key; `aws-cli` container on the `homelab_cloudflared` network, endpoint
`http://versitygw:7070`): `s3api put-bucket-policy` with `Principal: {"AWS": ["<agent access
key id>"]}` and resources `arn:aws:s3:::<bucket>` + `arn:aws:s3:::<bucket>/*`. `s3-agent`:
`GetObject`, `GetObjectAttributes`, `GetObjectTagging`, `ListBucket`,
`ListBucketMultipartUploads`, `ListMultipartUploadParts`, `PutObject`, `AbortMultipartUpload`.

## Caveats

- **Out-of-band edits** (Samba, Filebrowser, rsync) don't update S3-side ETags/metadata. The
  gateway still serves the bytes; only stored ETags can be stale.
- **`If-None-Match: *` only protects S3-written files.** VersityGW decides "exists" by the
  `user.etag` xattr; a file written out-of-band has none, so a conditional PUT overwrites it
  (2026-10-22: one `weatherorb-archive` file lost). Any write-capable key can therefore
  replace a Samba/rsync-written file in `ssd`/`hdd`.
  `weatherorb-archive` is sealed against this: `scripts/weatherorb-archive-seal.sh` (root
  systemd timer, every 10 min) backfills `user.etag` and sets `chattr +i` on every settled file.
- **Watchtower** updates `versity/versitygw:latest` like the rest of the stack.
- **Monitoring:** `S3 Gateway - Docker` + `S3 Gateway - HTTP` (`/_/health`, unauthenticated)
  in the Kuma `Files` group.
- The HomeLab host itself may not resolve `s3.jkrumm.com`; test from a tailnet client.
